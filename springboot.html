Introducción

¿Qué es Spring Boot?

Spring Boot permite crear aplicaciones Spring independientes, ejecutables y listas para producción con muy poca configuración manual.

  • Auto-configuración: detecta dependencias y crea la configuración base.
  • Starters: paquetes de dependencias coherentes para web, JPA, seguridad, testing, etc.
  • Servidor embebido: la aplicación se ejecuta como JAR con servidor incluido.
  • Características no funcionales: métricas, health checks, configuración externa y seguridad.

Idea central

Menos configuración repetitiva.
Más foco en reglas de negocio, pruebas y entrega de valor.

java -jar app.jar Convención > configuración Producción desde el diseño

Mejor práctica

1:N (Uno a Muchos)

Chef → Dish. Un Chef puede crear muchos Platos. La FK chef_id vive en la tabla Dishes.

N:M (Muchos a Muchos)

Client ↔ Dish. Un Cliente consume muchos platos, un plato es consumido por muchos. Requiere tabla dish_clients.

Cascada (CascadeType)

Si se elimina un Chef, se eliminan todos sus platos asociados automáticamente gracias a CascadeType.ALL.

Relaciones

Cómo pensar relaciones JPA

1:N

Chef → Dish. Un chef tiene muchos platos. La FK normalmente vive en Dish.

Dish.chef_id → Chef.id

N:M

Client ↔ Dish. Se requiere tabla intermedia para registrar consumos.

dish_clients(client_id, dish_id)

1:1

User ↔ Profile. Útil cuando una entidad complementa a otra.

profile.user_id UNIQUE

Regla de oro

No modele relaciones solo porque “existen en la vida real”. Modele las que necesita consultar, validar o persistir.

DTO + validación

No exponga entidades: use DTOs

Los DTOs protegen el contrato de la API y evitan filtrar campos internos, relaciones pesadas o datos sensibles.

  • Request DTO: datos que llegan del cliente.
  • Response DTO: datos que la API decide devolver.
  • Validación: evita datos inválidos antes de tocar la lógica de negocio.
public record ChefRequest( @NotBlank(message = "El nombre es obligatorio") @Size(max = 120) String name, @NotBlank String specialty, @Email String email ) {} public record ChefResponse( UUID id, String name, String specialty, String email ) {}

Manejo de errores

Errores consistentes con @ControllerAdvice

Una API profesional no devuelve trazas internas ni mensajes improvisados. Define un formato estándar de error.

{ "timestamp": "2026-07-03T18:30:00", "status": 404, "error": "NOT_FOUND", "message": "Chef no encontrado", "path": "/api/v1/chefs/123" }
@RestControllerAdvice class GlobalExceptionHandler { @ExceptionHandler(NotFoundException.class) ResponseEntity<ApiError> handleNotFound( NotFoundException ex, HttpServletRequest request) { ApiError error = ApiError.of( 404, "NOT_FOUND", ex.getMessage(), request.getRequestURI() ); return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error); } }
Spring Data JPA

Repositorios y consultas

  • JpaRepository: CRUD, paginación y ordenamiento sin escribir SQL.
  • Query Methods: consultas a partir del nombre del método.
  • @Query: JPQL o SQL nativo cuando se requiere control.
  • Pageable: paginación profesional.
interface DishRepository extends JpaRepository<Dish, UUID> { Page<Dish> findByChefId(UUID chefId, Pageable pageable); List<Dish> findByNameContainingIgnoreCase(String name); @Query(""" SELECT d FROM Dish d WHERE d.price BETWEEN :min AND :max ORDER BY d.price ASC """) List<Dish> findByPriceRange( @Param("min") BigDecimal min, @Param("max") BigDecimal max); }
Muchos a Muchos

Consulta compleja con @Query

Se usa @Query cuando aparecen agregados, proyecciones a DTO, o el nombre del método derivado sería impronunciable.

  • Doble JOIN: por la ManyToMany y por el chef.
  • GROUP BY: agrupa por plato.
  • HAVING: filtra sobre el agregado (el WHERE no puede).
  • new ...(): devuelve un DTO, no entidades.
@Query(""" SELECT new ….DishPopularityResponse( d.id, d.nombre, ch.nombre, d.precio, COUNT(DISTINCT cl.id), SUM(d.precio)) FROM Dish d JOIN d.clientes cl // ManyToMany JOIN d.chef ch // ManyToOne WHERE d.precio >= :precioMinimo GROUP BY d.id, d.nombre, ch.nombre, d.precio HAVING COUNT(DISTINCT cl.id) >= :minimo ORDER BY COUNT(DISTINCT cl.id) DESC """) List<DishPopularityResponse> ranking(…);
Muchos a Muchos

El mismo JOIN sin @Query

Spring Data arma el JOIN leyendo el nombre del método. No hay JPQL que mantener.

El _ marca dónde termina una propiedad y empieza la siguiente:

Clientes → atributo de Dish
Id → atributo de Client

// JOIN con la intermedia dish_clients List<Dish> findByClientes_Id(UUID clientId); // Doble JOIN + orden, sin una línea de JPQL List<Dish> findByClientes_IdAndChef_Id OrderByPrecioDesc(UUID cl, UUID ch); // COUNT y EXISTS también hacen el JOIN long countByClientes_Id(UUID clientId); boolean existsByIdAndClientes_Id( UUID dishId, UUID clientId);
Regla práctica: usar el método derivado mientras alcance; pasar a @Query cuando aparezcan GROUP BY, HAVING o proyecciones.
Rendimiento

El problema N+1

Las relaciones son LAZY: la colección no se trae hasta que alguien la toca.

Si el mapper la toca dentro de un bucle, se dispara una consulta por cada fila.

100 chefs = 101 consultas. Con open-in-view en true esto pasa en silencio.

// ❌ 1 consulta + N consultas chefRepository.findAll().stream() .map(ChefMapper::toResponse) // ↑ adentro toca getPlatos() .toList(); // ✅ 1 sola consulta con JOIN de carga @EntityGraph(attributePaths = {"platos"}) List<Chef> findAllBy();
Se llama findAllBy() y no findAll() porque findAll() es heredado de JpaRepository y no admite la anotación.
Rendimiento

@EntityGraph en la relación ManyToMany

Con @EntityGraph
// plato + chef en la misma consulta @EntityGraph(attributePaths = {"chef"}) List<Dish> findByClientes_Nombre(String n); // varios niveles: cliente → platos → chef @EntityGraph(attributePaths = { "platosConsumidos", "platosConsumidos.chef"}) List<Client> findAllBy();
Lo mismo escrito a mano
@Query(""" SELECT DISTINCT c FROM Client c LEFT JOIN FETCH c.platosConsumidos d LEFT JOIN FETCH d.chef """) List<Client> findAllConPlatosYChef();

DISTINCT porque el FETCH duplica al cliente una vez por plato. LEFT para no perder a los que aún no consumieron nada.

Transacciones

open-in-view: el default que tapa problemas

Spring Boot trae open-in-view: true: deja la sesión de Hibernate abierta durante todo el request.

  • Hace que todo "funcione", pero esconde el N+1.
  • Retiene la conexión a la BD mientras se serializa el JSON.
  • Spring avisa con un warning al arrancar.
spring: jpa: open-in-view: false

Al apagarlo, la sesión vive solo lo que dura la transacción. Por eso hay que ser explícito con @Transactional.

Transacciones

@Transactional: dónde vive la sesión

// ❌ sin transacción al mapear public ClientResponse actualizar(UUID id) { Client c = buscarPorId(id); // ↑ abre y cierra la tx return ClientMapper.toResponse(c); } // LazyInitializationException al leer // getPlatosConsumidos() fuera de la sesión
// ✅ la tx cubre también el mapeo @Transactional public ClientResponse actualizar(UUID id) { … } // lecturas: readOnly evita el dirty checking @Transactional(readOnly = true) public List<ClientResponse> obtenerTodos() { … }

La regla: @Transactional resuelve la corrección (que no explote). @EntityGraph resuelve el rendimiento (que no sean N consultas). Se usan juntos.

@Transactional solo funciona en métodos públicos llamados desde otro bean: Spring lo implementa con un proxy.
IoC

Inyección de dependencias

Inversión de Control: Spring crea y conecta los objetos. El código depende de abstracciones y no de instancias creadas manualmente.

  • Preferir inyección por constructor.
  • Usar final para dependencias obligatorias.
  • Evitar @Autowired sobre atributos cuando no sea necesario.
// ❌ Acoplamiento fuerte class ChefController { private ChefService service = new ChefServiceImpl(); } // ✅ Dependencia explícita y testeable @Service @RequiredArgsConstructor class ChefService { private final ChefRepository repository; private final ChefMapper mapper; }
Concepto Clave

¿Qué es exactamente un "Bean"?

Un Bean es un objeto Java cuyo ciclo de vida lo administra el contenedor de Spring.

  • Creación: no usás new MiClase(). Spring escanea @Component, @Service, etc. y crea la instancia al iniciar.
  • Configuración: le inyecta sus dependencias automáticamente.
  • Gestión: por defecto son Singleton: una única instancia compartida.
  • Destrucción: Spring los destruye al apagar la app.

La analogía del Restaurante

Spring es el Gerente. Vos escribís las "descripciones de cargo" (las clases).

El Gerente contrata a las personas (crea los Beans), les entrega las herramientas que necesitan (Inyección de Dependencias) y coordina que trabajen juntas, sin que vos lo hagas a mano.

Configuración

application.yml y perfiles

Los perfiles separan ambientes y evitan mezclar credenciales, puertos o bases de datos.

dev

PostgreSQL local, logs detallados, ddl-auto: update.

test

H2 en memoria, base limpia, pruebas automatizadas.

prod

Variables de entorno, ddl-auto: validate, logs controlados.

Cómo se debe llamar el archivo
application.yml ← base, siempre application-dev.yml ← perfil "dev" application-test.yml ← perfil "test" application-prod.yml ← perfil "prod" application-docker.yml ← perfil "docker" application-<perfil>.yml ↑ guion, NO guion bajo ni punto ↑ distingue mayúsculas

Si el nombre no coincide, Spring no avisa: ignora el archivo y arranca con la config base.

application.yml se carga siempre y guarda lo común; el archivo del perfil se aplica encima y pisa lo que repita.
Configuración

Cómo se activa un perfil

Las 4 formas, de menor a mayor prioridad
// 1. En el propio application.yml spring: profiles: active: dev // 2. Variable de entorno (Docker, CI) SPRING_PROFILES_ACTIVE=prod // 3. Argumento al ejecutar java -jar app.jar --spring.profiles.active=prod // 4. Propiedad de la JVM java -Dspring.profiles.active=prod -jar app.jar
En los tests
@SpringBootTest @ActiveProfiles("test") class MiTest { … }

Cuidado con el nombre de las variables: usar ${DB_URL} y no ${SPRING_DATASOURCE_URL}. Este último normaliza a spring.datasource.url, que es la propiedad que se está definiendo: queda una autorreferencia, el placeholder no se resuelve y llega el texto literal al driver.

Se pueden activar varios a la vez: --spring.profiles.active=prod,metricas

Seguridad

Spring Security: mínimo viable

No toda API necesita JWT desde el día 1, pero toda API debe pensar en autenticación, autorización y protección de endpoints.

  • Autenticación: ¿quién eres?
  • Autorización: ¿qué puedes hacer?
  • Roles: ADMIN, USER, MANAGER.
  • JWT: común en APIs stateless.
@Bean SecurityFilterChain security(HttpSecurity http) throws Exception { return http .csrf(csrf -> csrf.disable()) .authorizeHttpRequests(auth -> auth .requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll() .requestMatchers(HttpMethod.GET, "/api/v1/dishes/**").permitAll() .requestMatchers("/api/v1/admin/**").hasRole("ADMIN") .anyRequest().authenticated() ) .build(); }
