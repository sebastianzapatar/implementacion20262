Introducción

¿Qué es Spring Boot?

Spring Boot permite crear aplicaciones Spring independientes, ejecutables y listas para producción con muy poca configuración manual.

  • Auto-configuración: detecta dependencias y crea la configuración base.
  • Starters: paquetes de dependencias coherentes para web, JPA, seguridad, testing, etc.
  • Servidor embebido: la aplicación se ejecuta como JAR con servidor incluido.
  • Características no funcionales: métricas, health checks, configuración externa y seguridad.

Idea central

Menos configuración repetitiva.
Más foco en reglas de negocio, pruebas y entrega de valor.

java -jar app.jar Convención > configuración Producción desde el diseño

Spring Boot 4.x: lo que conviene saber

Base tecnológica

Spring Boot 4 se apoya en Spring Framework 7, Jakarta EE 11 y requiere Java 17 o superior.

Modularidad

Los starters y módulos son más específicos. Esto mejora claridad, pero exige revisar dependencias al migrar.

Clientes HTTP

Incluye soporte de auto-configuración para HTTP Service Clients basados en interfaces anotadas.

Migración

Antes de subir de versión: actualizar a la última 3.5.x, revisar deprecaciones y validar propiedades.

Nota didáctica: si el curso trabaja con Spring Boot 3.x, los conceptos siguen siendo válidos; la diferencia está en versiones y algunos paquetes.

Estructura recomendada

Organización del proyecto

src/ ├── main/ │ ├── java/com/eia/restaurant/ │ │ ├── RestaurantApplication.java │ │ ├── chef/ │ │ │ ├── controller/ │ │ │ ├── service/ │ │ │ ├── repository/ │ │ │ ├── entity/ │ │ │ ├── dto/ │ │ │ └── mapper/ │ │ ├── dish/ │ │ └── common/ │ │ ├── exception/ │ │ └── config/ │ └── resources/ │ ├── application.yml │ ├── application-dev.yml │ ├── application-test.yml │ └── application-prod.yml └── test/ └── java/com/eia/restaurant/

Mejor práctica

  • Paquetes por feature: chef, dish, client. Escala mejor que separar todo por capas globales.
  • DTOs con records: contratos inmutables y claros.
  • common: excepciones, configuración, seguridad, constantes y utilidades compartidas.
  • Perfiles: separar configuración de desarrollo, pruebas y producción.

JPA / Hibernate

Anotaciones de persistencia

AnotaciónQué hace
@EntityRepresenta una tabla.
@TablePersonaliza el nombre de tabla.
@IdClave primaria.
@GeneratedValueGeneración automática de ID.
@ColumnConfigura columna: nullable, unique, length.
@ManyToOneMuchos registros pertenecen a uno.
@OneToManyUn registro tiene muchos hijos.
@ManyToManyRelación N:M.
@JoinColumnLlave foránea.
@Entity @Table(name = "dishes") @Getter @Setter @NoArgsConstructor class Dish { @Id @GeneratedValue(strategy = GenerationType.UUID) private UUID id; @Column(nullable = false, length = 120) private String name; @Column(nullable = false, precision = 10, scale = 2) private BigDecimal price; @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "chef_id", nullable = false) private Chef chef; }
Relaciones

Cómo pensar relaciones JPA

1:N

Chef → Dish. Un chef tiene muchos platos. La FK normalmente vive en Dish.

Dish.chef_id → Chef.id

N:M

Client ↔ Dish. Se requiere tabla intermedia para registrar consumos.

client_dish(client_id, dish_id)

1:1

User ↔ Profile. Útil cuando una entidad complementa a otra.

profile.user_id UNIQUE

Regla de oro

No modele relaciones solo porque “existen en la vida real”. Modele las que necesita consultar, validar o persistir.

DTO + validación

No exponga entidades: use DTOs

Los DTOs protegen el contrato de la API y evitan filtrar campos internos, relaciones pesadas o datos sensibles.

  • Request DTO: datos que llegan del cliente.
  • Response DTO: datos que la API decide devolver.
  • Validación: evita datos inválidos antes de tocar la lógica de negocio.
public record ChefRequest( @NotBlank(message = "El nombre es obligatorio") @Size(max = 120) String name, @NotBlank String specialty, @Email String email ) {} public record ChefResponse( UUID id, String name, String specialty, String email ) {}
Manejo de errores

Errores consistentes con @ControllerAdvice

Una API profesional no devuelve trazas internas ni mensajes improvisados. Define un formato estándar de error.

{ "timestamp": "2026-07-03T18:30:00", "status": 404, "error": "NOT_FOUND", "message": "Chef no encontrado", "path": "/api/v1/chefs/123" }
@RestControllerAdvice class GlobalExceptionHandler { @ExceptionHandler(NotFoundException.class) ResponseEntity<ApiError> handleNotFound( NotFoundException ex, HttpServletRequest request) { ApiError error = ApiError.of( 404, "NOT_FOUND", ex.getMessage(), request.getRequestURI() ); return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error); } }
Spring Data JPA

Repositorios y consultas

  • JpaRepository: CRUD, paginación y ordenamiento sin escribir SQL.
  • Query Methods: consultas a partir del nombre del método.
  • @Query: JPQL o SQL nativo cuando se requiere control.
  • Pageable: paginación profesional.
interface DishRepository extends JpaRepository<Dish, UUID> { Page<Dish> findByChefId(UUID chefId, Pageable pageable); List<Dish> findByNameContainingIgnoreCase(String name); @Query(""" SELECT d FROM Dish d WHERE d.price BETWEEN :min AND :max ORDER BY d.price ASC """) List<Dish> findByPriceRange( @Param("min") BigDecimal min, @Param("max") BigDecimal max); }
IoC

Inyección de dependencias

Inversión de Control: Spring crea y conecta los objetos. El código depende de abstracciones y no de instancias creadas manualmente.

  • Preferir inyección por constructor.
  • Usar final para dependencias obligatorias.
  • Evitar @Autowired sobre atributos cuando no sea necesario.
// ❌ Acoplamiento fuerte class ChefController { private ChefService service = new ChefServiceImpl(); } // ✅ Dependencia explícita y testeable @Service @RequiredArgsConstructor class ChefService { private final ChefRepository repository; private final ChefMapper mapper; }
Lombok

Lombok: útil, pero con criterio

Úselo para reducir ruido

@GetterGetters
@SetterSetters
@NoArgsConstructorConstructor requerido por JPA
@BuilderCreación fluida
@RequiredArgsConstructorInyección por constructor

Evite errores comunes

  • No usar @Data ciegamente en entidades JPA.
  • Cuidado con toString en relaciones bidireccionales.
  • Cuidado con equals/hashCode usando colecciones lazy.
  • Para DTOs, preferir record cuando aplique.

Swagger / OpenAPI

Una API 10/10 debe poder probarse, entenderse y compartirse sin leer todo el código.

  • Documenta endpoints, parámetros, cuerpos y respuestas.
  • Facilita pruebas desde navegador.
  • Sirve como contrato entre backend y frontend.

Seguridad

Spring Security: mínimo viable

No toda API necesita JWT desde el día 1, pero toda API debe pensar en autenticación, autorización y protección de endpoints.

  • Autenticación: ¿quién eres?
  • Autorización: ¿qué puedes hacer?
  • Roles: ADMIN, USER, MANAGER.
  • JWT: común en APIs stateless.
@Bean SecurityFilterChain security(HttpSecurity http) throws Exception { return http .csrf(csrf -> csrf.disable()) .authorizeHttpRequests(auth -> auth .requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll() .requestMatchers(HttpMethod.GET, "/api/v1/dishes/**").permitAll() .requestMatchers("/api/v1/admin/**").hasRole("ADMIN") .anyRequest().authenticated() ) .build(); }

Buenas prácticas

Checklist para que la API sea 10/10

Diseño

  • Endpoints REST consistentes.
  • DTOs separados de entidades.
  • Validaciones en entrada.
  • Errores estandarizados.

Código

  • Service con reglas de negocio.
  • Inyección por constructor.
  • Transacciones donde corresponde.
  • No exponer stack traces al usuario.

Datos

  • Paginación en listados.
  • Índices en búsquedas frecuentes.
  • Evitar N+1 queries.
  • Migraciones con Flyway o Liquibase.

Producción

  • Perfiles separados.
  • Docker Compose para desarrollo.
  • Actuator y logs.
  • Pruebas unitarias e integración.
